# 🏠 RentEasy — Платформа для аренды жилья в Европе

RentEasy — это полноценное веб-приложение для поиска и сдачи жилья в аренду по всей Европе. Платформа соединяет владельцев недвижимости с потенциальными арендаторами, предлагая удобный поиск с фильтрами, чат в реальном времени, интерактивные карты и безопасную двухфакторную аутентификацию.

**Живое демо:** http://13.50.199.197

## ✨ Возможности

- **🔐 Двухфакторная аутентификация** — при каждом входе на почту приходит одноразовый код

- **⭐ Отзывы** — только подтверждённые арендаторы могут оставлять оценки
- **🔍 Поиск и фильтры** — по городу, цене, типу жилья, удобствам, рейтингу
- **📱 Тёмный интерфейс** — адаптивный дизайн с тёмной темой

## 🏗️ Архитектура

Проект разделён на несколько независимых сервисов, каждый в своём Docker контейнере:

```
Браузер пользователя
        │
        ▼
┌─────────────────┐
│   Nginx :80     │  ← единая точка входа
│                 │
│  /              │──→ React SPA (статические файлы)
│  /apartments/   │──→ Django API
│  /auth/         │──→ Django API
│  /chat/         │──→ Django API
│  /ws/           │──→ Django Channels (WebSocket)
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Daphne :8000   │  ← ASGI сервер Django
│  (Django)       │
└────────┬────────┘
         │
    ┌────┴─────┐
    │          │
    ▼          ▼
┌───────┐  ┌───────┐
│ MySQL │  │ Redis │
│(данные│  │(кэш + │
│      )│  │  WS)  │
└───────┘  └───┬───┘
               │
               ▼
           ┌───────┐
           │  S3   │
           │(фото) │
           └───────┘
```

**Почему именно так?**

- **Nginx** стоит перед всем — он эффективно раздаёт статику React и проксирует API запросы к Django
- **Daphne** вместо стандартного Gunicorn — потому что Django Channels требует ASGI сервер для поддержки WebSocket
- **Redis** используется для двух разных целей: временное хранение 2FA кодов и передача сообщений между WebSocket соединениями
- **S3** для медиафайлов — EC2 диск ограничен, S3 дешёвый и неограниченный

## 🔐 Как работает аутентификация

Используется JWT (JSON Web Token) — это стандарт для передачи информации о пользователе без хранения сессий в базе данных.

### Почему JWT, а не сессии?

В стандартном Django при каждом запросе сервер ищет сессию в базе данных — это дополнительный запрос к БД. JWT самодостаточен: сервер проверяет подпись математически, не обращаясь к базе. Это быстрее и лучше масштабируется. Кроме того, наш фронтенд (React) отдельный от бэкенда — JWT в заголовке `Authorization` работает чище чем куки между разными доменами.

### Полный цикл входа

```
1. Пользователь вводит email + пароль
        │
        ▼ POST /auth/login/
   Django проверяет credentials
        │
        ▼
   Генерирует случайный 6-значный код
        │
   ┌────┴─────────────────────┐
   │                          │
   ▼                          ▼
Сохраняет в Redis          Отправляет на email
cache.set("2fa:1",            через Gmail SMTP
  "483920", 300)
(живёт 5 минут)

2. Пользователь вводит код из письма
        │
        ▼ POST /auth/verify/
   Django читает из Redis
   Сравнивает коды
   Удаляет код из Redis
        │
        ▼
   Создаёт два токена:
   ┌─────────────────────────────────────┐
   │ access token  — живёт 60 минут      │
   │ refresh token — живёт 7 дней        │
   └─────────────────────────────────────┘
        │
        ▼
   Фронтенд сохраняет:
   access  → в памяти JS (теряется при закрытии вкладки)
   refresh → в localStorage (переживает перезагрузку)

3. Каждый API запрос:
   Authorization: Bearer eyJhbGci...

4. При перезагрузке страницы:
   Читает refresh из localStorage
   → POST /api/token/refresh/
   → Получает новый access токен
   → Загружает данные пользователя
```

### Структура JWT токена

Токен состоит из трёх частей через точку:
```
eyJhbGciOiJIUzI1NiJ9  .  eyJ1c2VyX2lkIjoxfQ  .  подпись
      Header                    Payload
  (алгоритм)            (user_id, время жизни)
```

Подпись создаётся с `SECRET_KEY` из настроек Django — без него токен нельзя подделать.

## 💬 Как работает чат

Обычный HTTP работает по схеме запрос-ответ: клиент спрашивает — сервер отвечает. Для чата это не подходит — сервер не может сам отправить сообщение клиенту. WebSocket создаёт постоянное двустороннее соединение.

### Полный путь сообщения

```
Пользователь A пишет "Привет" → нажимает Enter
        │
        ▼
ws.send('{"text": "Привет"}')
        │
        ▼ Nginx /ws/ → Django Channels
        │
        ▼
Consumer.receive() — получает сообщение
        │
   ┌────┴──────────────────────┐
   │                           │
   ▼                           ▼
Сохраняет в MySQL       group_send() в Redis
Message.objects           группа "chat_1"
  .create(...)
                               │
                    Redis рассылает всем в "chat_1"
                               │
                    ┌──────────┴──────────┐
                    ▼                     ▼
            Consumer A              Consumer B
            chat_message()          chat_message()
                    │                     │
                    ▼                     ▼
            self.send(json)         self.send(json)
                    │                     │
                    ▼                     ▼
            ws.onmessage()          ws.onmessage()
            (сообщение у A)         (сообщение у B)
```

### Почему Redis в чате?

Если пользователь A и пользователь B подключены к одному процессу Django — можно передать сообщение напрямую. Но если они на разных процессах (или серверах) — нужен посредник. Redis выступает общей шиной: каждый Consumer подписан на группу `chat_1`, Redis доставляет сообщения всем подписчикам независимо от того на каком процессе они запущены.

### Аутентификация WebSocket

Браузер не может добавить заголовок `Authorization` в WebSocket запрос — это ограничение браузерного API. Поэтому токен передаётся в URL:
```
ws://host/ws/chat/1/?token=eyJhbGci...
```
Специальный middleware перехватывает запрос, проверяет токен теми же методами что и REST API, и добавляет пользователя в `scope` — объект с информацией о соединении.

## ☁️ Как работает AWS S3

Когда пользователь загружает фото квартиры:

```
Пользователь выбирает файл
        │
        ▼
POST /apartments/:id/images/
  (файл в теле запроса)
        │
        ▼
Django получает файл
        │
        ▼
django-storages + boto3
автоматически загружает в S3
        │
        ▼
В базе данных сохраняется путь:
"apartments/photo.jpg"
        │
        ▼
MEDIA_URL + путь = публичная ссылка:
https://bucket.s3.region.amazonaws.com/apartments/photo.jpg
```

Файлы никогда не хранятся на EC2 сервере — только в S3. Это важно потому что при пересборке Docker контейнеров локальные файлы теряются. S3 хранит данные надёжно и независимо от сервера.

## 🚀 Деплой

### Требования
- Сервер с Ubuntu, Docker и Docker Compose
- Файл `.env.prod` с переменными окружения
- Репозиторий на GitHub

### Первый деплой

```bash
# Подключиться к серверу
ssh -i key.pem ubuntu@your-server-ip

# Клонировать репозиторий
git clone https://github.com/KiviPY/rent_apartments_project.git
cd rent_apartments_project

# Создать файл с переменными окружения
nano .env.prod

# Собрать и запустить все контейнеры
sudo docker compose -f docker-compose.prod.yml up -d --build

# Применить миграции базы данных
sudo docker compose -f docker-compose.prod.yml exec backend python manage.py migrate
```

### Обновление после изменений

```bash
# Запушить изменения на GitHub (локально)
git add .
git commit -m "description"
git push

# На сервере подтянуть и пересобрать
git pull
sudo docker compose -f docker-compose.prod.yml down -v
sudo docker builder prune -af
sudo docker compose -f docker-compose.prod.yml up -d --build
```

### Что происходит при запуске

```
docker compose up --build
        │
   ┌────┴────────────────────────────────┐
   │    Собирает 2 Docker образа:        │
   │    1. Backend (Python + Django)     │
   │    2. Frontend (Node → npm build)   │
   └────┬────────────────────────────────┘
        │
   Запускает 4 контейнера:
   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
   │ backend  │ │ frontend │ │  redis   │ │  nginx   │
   │          │ │(собирает │ │          │ │          │
   │ migrate  │ │  билд и  │ │          │ │  ждёт    │
   │ static   │ │ выходит) │ │          │ │  готов.  │
   │ daphne   │ └──────────┘ └──────────┘ └──────────┘
   └──────────┘
```

Frontend контейнер собирает React приложение (`npm run build`), кладёт файлы в Docker volume и завершается — это нормально. Nginx читает эти файлы из volume и отдаёт браузеру.

## 🔒 Безопасность

- **JWT токены** вместо сессий — access токен живёт 60 минут
- **2FA при каждом входе** — одноразовый код на email
- **Пароли хешируются** Django (алгоритм PBKDF2)
- **S3 с Bucket Policy** — файлы публично читаемы, но не перезаписываемы
- **CORS** настроен только для домена приложения
- **Секреты в `.env.prod`** — не попадают в Git
- **`.pem` ключи в `.gitignore`** — SSH ключи не попадают в репозиторий
- **`DEBUG=False`** на продакшне — не показывает внутренние ошибки пользователям
